# MySpott: Architecture

## Overview
One Flask REST API serves the website, the Android app and the iOS app.
Business rules live in a service layer so web and API behave identically.

    Website (Jinja2/Bootstrap/JS)     Expo app (Android, iOS)
                  \                        /
                   Flask REST API (/api/v1)
            auth, permissions, validation, moderation
              /          |            \
       PostgreSQL   Image storage   External services (email, maps/places)

## Stack
- Backend: Python, Flask (application factory + blueprints), Flask-SQLAlchemy, Flask-Migrate
- Database: PostgreSQL (SQLite only for early local tests)
- Web: Jinja2, HTML/CSS/JS, Bootstrap 5 selectively
- Mobile: React Native with Expo
- Images: Pillow / OpenCV, perceptual hashing
- Tests: pytest and the Flask test client

## Working assumptions (change later if needed)
- Roles: seeker or owner chosen at signup; admins created only by a secure command-line script
- New listings publish immediately unless flagged; flagged listings wait for review
- Listings expire after 60 days with a renew option
- Minimum password length: 8
- One WhatsApp number per owner, stored in E.164 format (default +91)
- Maps: Leaflet + OpenStreetMap for the MVP, behind a service layer so Google Maps can replace it
- Distance: straight-line, labelled as such in the UI
- Room classification is deferred; owners pick the photo category
- Max 10 images per listing, 5 MB upload limit before compression
- Duplicates are flagged for review, never auto-merged

- Secrets only in environment variables; `.env` is git-ignored

## Database (added in Phase 2)
- Local PostgreSQL for development (database `myspott_dev`), a separate `myspott_test` for automated tests.
- SQLAlchemy models live in `app/models/`; shared extension objects in `app/extensions.py`.
- Schema changes are made only through migrations (`flask --app run db migrate` / `upgrade`); the `migrations/`
  folder is committed to Git.
- Constraint and index names follow a fixed naming convention so migrations stay clean.
- `users` table: id, name, email (unique, stored lowercase), password_hash (never plain text), role
  (seeker / owner / admin, enforced by a database check), account_status (active / suspended),
  email_verified_at, whatsapp_e164, created_at, updated_at, last_login_at.
- Settings: DATABASE_URL and TEST_DATABASE_URL in `.env` (never committed). The app refuses to start without them.
